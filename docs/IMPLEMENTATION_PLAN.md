# Contract AI Analyzer — план реализации

Этапы соответствуют промптам `01`–`09`. Каждый этап завершается запуском тестов, линтеров и сборки, обновлением `IMPLEMENTATION_STATUS.md` и отдельным Git-коммитом. Следующий этап начинается только после этого.

Архитектура — [ARCHITECTURE.md](ARCHITECTURE.md), угрозы и меры — [THREAT_MODEL.md](THREAT_MODEL.md).

## Этап 02 — Каркас, БД, Docker

Результат:
- `backend/`: pyproject (FastAPI, SQLAlchemy 2 async + psycopg 3, Alembic, pydantic-settings, structlog), app factory, конфигурация с проверкой обязательных параметров, единый формат ошибок, request ID middleware, security headers, логирование с редактированием, `/api/health/live|ready`.
- ORM-модели и первая миграция для всех сущностей из ARCHITECTURE §5 (схема целиком сразу, чтобы последующие этапы не требовали разрушительных миграций).
- Очередь задач (`Job`) — базовые claim/heartbeat/reaper + каркас worker'а.
- `frontend/`: Vite + React + TS strict + Tailwind + Router + TanStack Query, страница состояния системы на реальном readiness API (без фиктивных данных), oxlint, Vitest.
- `converter/`: Dockerfile и минимальный HTTP-сервис (реальная логика — этап 04).
- `compose.yaml` (db, migrate, backend, worker, converter, frontend, profile `ollama`), сети и volumes, healthchecks, non-root; `.env.example`, `.dockerignore`, `.gitattributes` (LF для `*.sh`, Dockerfile, конфигов).
- `docs/OPERATIONS.md`: локальный запуск, backup/restore PostgreSQL и storage.

Проверки: `ruff`, `mypy`, `pytest` (unit: конфиг, формат ошибок, редактирование логов, health), `alembic upgrade head` на чистой БД (если Docker доступен), `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, `docker compose build`/`up` + проверка health (если Docker доступен).

## Дополнительный этап 08A — Автоматические внешние бэкапы

Не входит в промпты 00–09; добавлен по запросу владельца продукта (2026-10-15). Выполняется после этапа 08 и до финальной приёмки 09, чтобы 09 проверил и его. Зависит только от этапа 02 (`deploy/backup.sh`, `deploy/restore.sh`), поэтому может быть выполнен и раньше по отдельной команде.

Результат:
- **Шифрование**: бэкап (`db.dump` + `storage.tar.gz`) шифруется перед выгрузкой. На сервере хранится только публичный ключ получателя; приватный ключ хранится у администратора вне сервера.
- **Выгрузка за пределы сервера**: шаг в `backup.sh`; цель выбирается параметром `BACKUP_TARGET` (`s3` через `rclone` в отдельном контейнере без установки инструментов на хост, или `local` — каталог на другом диске/NAS). Учётные данные не логируются. После загрузки проверяется контрольная сумма на стороне хранилища.
- **Расписание**: готовые unit-файлы systemd timer и пример строки crontab для хоста (Docker socket контейнерам не выдаётся); защита от параллельного запуска (`flock`); лог запусков; уведомление об ошибке (webhook/e-mail).
- **Ротация**: параметры хранения в `.env`. Локальные копии удаляются только после успешного создания и выгрузки нового бэкапа; последняя успешная копия не удаляется никогда. Во внешнем хранилище рекомендуется ротация правилами хранилища (lifecycle, versioning/object lock), а не скриптом с сервера — чтобы взлом сервера не позволял стереть копии.
- **Восстановление**: `restore.sh` принимает зашифрованный бэкап (локальный или скачанный из хранилища) и расшифровывает его ключом администратора.
- Документация в `docs/OPERATIONS.md`: настройка, ротация ключей, проверка восстановления, связь срока хранения бэкапов с удалением документов.

Проверки: валидация параметров (некорректные значения → отказ с понятной ошибкой), шифрование/расшифровка, выгрузка и скачивание для `BACKUP_TARGET=s3` (локальный MinIO в Docker) и `BACKUP_TARGET=local` (отдельный каталог), установка/обновление/удаление расписания из `BACKUP_SCHEDULE`, ротация по `BACKUP_KEEP_*`, ротация (сохраняется последняя успешная копия; при неудачной выгрузке локальные копии не удаляются), защита от параллельного запуска, полный цикл backup → upload → удаление локальных копий → download → restore с проверкой данных. Выгрузка в реальное хранилище — только при наличии доступа; иначе явно отмечается как непроверенная.

Настройки (решение владельца продукта, 2026-10-15): место выгрузки, частота и сроки хранения задаются параметрами, а не зашиты в скрипты. Параметры — в `.env` (или отдельном `deploy/backup.env`), проверяются при запуске: при некорректном значении бэкап не начинается и пишется понятная ошибка.

| Параметр | Значения | По умолчанию |
|---|---|---|
| `BACKUP_TARGET` | `s3` — S3-совместимое хранилище; `local` — каталог (например, примонтированный NAS/второй диск); `none` — только локальные копии на сервере | `none` |
| `BACKUP_S3_ENDPOINT`, `BACKUP_S3_BUCKET`, `BACKUP_S3_PREFIX`, `BACKUP_S3_REGION`, `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY` | для `s3`; секреты не логируются | — |
| `BACKUP_LOCAL_TARGET_DIR` | для `local`: абсолютный путь, отличный от каталога локальных копий | — |
| `BACKUP_DIR` | каталог локальных копий на сервере | `./backups` |
| `BACKUP_ENCRYPTION_RECIPIENT` | публичный ключ `age`; обязателен при `s3`/`local` | — |
| `BACKUP_SCHEDULE` | расписание в формате cron (`0 3 * * *`) | `0 3 * * *` (ежедневно в 03:00) |
| `BACKUP_KEEP_LOCAL` | число копий на сервере | `7` |
| `BACKUP_KEEP_REMOTE_DAILY`, `BACKUP_KEEP_REMOTE_WEEKLY`, `BACKUP_KEEP_REMOTE_MONTHLY` | схема хранения во внешнем хранилище | `7`, `4`, `6` |
| `BACKUP_REMOTE_PRUNE` | `script` — старые копии удаляет скрипт по схеме выше; `lifecycle` — удаление настроено правилами хранилища, скрипт ничего не удаляет (безопаснее при взломе сервера) | `script` для `local`, `lifecycle` для `s3` (с инструкцией по настройке правил) |
| `BACKUP_NOTIFY_WEBHOOK` | URL для уведомления об ошибке; пусто — только лог и ненулевой код выхода | пусто |

- Частота применяется командой `deploy/backup-schedule.sh install`: она читает `BACKUP_SCHEDULE` и создаёт/обновляет systemd timer (или строку crontab). После изменения параметра команда запускается повторно; `uninstall` и `status` — отключение и просмотр.
- Изменение сроков хранения применяется со следующего запуска; удаление всегда выполняется только после успешного нового бэкапа, последняя успешная копия не удаляется.
- Шифрование — `age`.

## Этап 09 — Финальная приёмка

Проход по `ACCEPTANCE_CHECKLIST.md` с фактической проверкой каждого пункта, исправления без риска потери данных, итоговый отчёт с реальными результатами и перечнем непроверенного.

## Решения, принятые на этапе 01 (могут быть пересмотрены по запросу)

1. Очередь задач в PostgreSQL, без Redis.
2. Admin не читает чужие договоры без явного доступа; Superadmin — может, с аудитом.
3. Страницы DOCX/DOC — по сохранённой разметке Word, иначе по рендеру LibreOffice, с пометкой источника; если не удаётся — не указываются.
4. Смысловая проверка цитат — отдельный вызов модели-верификатора; по умолчанию та же модель, что и анализ (для облачной модели это дополнительная передача уже отправленных фрагментов тому же провайдеру — входит в то же согласие).
5. Название документа не пишется в аудит.
6. PDF-экспорт через reportlab (без HTML-рендера), чтобы исключить HTML-injection и тяжёлые системные зависимости.
7. Python 3.13 в образах (совпадает с машиной разработки).
