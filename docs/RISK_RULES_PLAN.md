# Дополнительный этап 11 — Правила рисков организации в категориях анализа

Статус: **план, составлен 2026-10-23** по запросу владельца продукта; решения §1 подтверждены владельцем 2026-10-23 (все — по умолчанию). Этап не входит в промпты 00–09; выполняется по отдельной команде владельца. Правила проекта (`00-master-and-workflow.md`, CLAUDE.md) действуют полностью: без демо-данных, дословные цитаты с реальным fragment ID и страницей, текст договора — недоверенные данные, без разрушительных миграций, в конце этапа — реальные проверки и раздел в `docs/IMPLEMENTATION_STATUS.md`.

## 0. Цель

Организация описывает свои типовые риски («неустойка выше 0,1 % в день», «срок оплаты больше 30 дней», «нет условия о приёмке по акту») и включает их в анализ. Правила видны в форме нового анализа внутри блока «Категории рисков» — под своей категорией, отдельными флажками.

Это **не дообучение модели** и **не изменение базового системного промпта**. Базовые промпты (`backend/app/analysis/prompts.py`) остаются неизменными и версионируемыми; выбранные правила добавляются отдельным ограниченным блоком. Все требования к рискам (дословная цитата, проверка шага A, проверка верификатором) действуют для рисков по правилам так же, как для остальных.

## 1. Решения владельца (2026-10-23)

Все вопросы ниже владелец решил по умолчанию.

| # | Вопрос | Решение |
|---|---|---|
| 1 | Кто создаёт и меняет правила | Admin и Superadmin (как модели, `can_manage_models`); Analyst и Viewer — только видят включённые правила в форме анализа |
| 2 | Помощник «Подготовить с помощью модели» (свободное описание → поля правила) в первой версии | **Нет**: поля заполняются вручную; помощник — отдельной доработкой (§9) |
| 3 | Ограничения | до 100 правил в каталоге, до 20 правил в одном анализе; описание правила ≤ 1000 символов; блок правил в промпте ≤ 8000 символов (иначе 422 с понятной ошибкой) |
| 4 | Отметка в форме по умолчанию | все включённые правила отмечены; у правила есть флаг «предлагать по умолчанию» |
| 5 | Где страница управления | отдельная страница «Правила» (`/admin/risk-rules`) в меню для Admin/Superadmin; в «Настройках» — ссылка |
| 6 | Маскировка текста правил для облачных моделей | не применяется (правила пишет администратор, а не договор); в форме правила — предупреждение не указывать персональные и конфиденциальные данные |

Прочие решения по умолчанию:
- Правила не удаляются, а архивируются (данные и история сохраняются; на старые анализы ссылается snapshot).
- Правило привязано ровно к одной существующей категории `RiskCategory`; без подходящей — `other`. Новые категории этап не вводит.
- Снятие категории в форме снимает и её правила: правило анализируется только в рамках своей категории.

## 2. Как работает (кратко)

```
Admin: правило (категория, тип, что искать, признаки, уровень, рекомендация) → включено
  → форма анализа: категории + правила под ними (флажки)
  → запуск: выбранные правила копируются в snapshot анализа (текст + ревизия)
  → промпты chunks / cross_section: блок <org_rules> с правилами выбранных категорий
  → ответ модели: риск может указать rule_code; сервер проверяет код по списку из snapshot
  → цитаты, шаг A, верификатор — без изменений
  → отчёт и экспорт: отметка «Правило RR-003 …», фильтр по правилу, список применённых правил
```

## 3. Правило: поля

| Поле | Ограничение | Назначение |
|---|---|---|
| `code` | `RR-001`… (генерируется, уникален, не меняется) | ссылка в ответе модели и в отчёте |
| `title` | ≤ 200 | название в форме и отчёте |
| `category` | `RiskCategory` | в какой категории показывать и анализировать |
| `kind` | `clause_risk` \| `missing_clause` \| `any` | где применять: в анализе фрагментов, в поиске отсутствующих условий или в обоих |
| `description` | ≤ 1000 | что считать риском (основной текст для модели) |
| `signs` | ≤ 1000, необязательно | признаки и примеры формулировок |
| `severity` | `RiskSeverity` или null | рекомендуемый уровень; модель может отступить с объяснением в `reason` |
| `recommendation` | ≤ 1000, необязательно | типовая рекомендация организации |
| `enabled` | bool | показывать ли в форме анализа |
| `default_selected` | bool | отмечено ли по умолчанию |
| `archived_at` | timestamp или null | архив |

## 4. Модель данных (миграция 0009, только добавление)

- `risk_rules`: поля §3 + `id`, `version` (`version_id_col`, как `ModelConfig`), `created_by_id`, `updated_by_id`, `created_at`, `updated_at`. Код — из последовательности `risk_rule_code_seq`.
- Изменения — `config_revisions` (`entity_type="risk_rule"`, diff полей), аудит `risk_rule.created|updated|enabled|disabled|archived` (без текста правила в `details` — только код и изменённые поля).
- `risks.rule_code` (VARCHAR(16), nullable) — код правила, по которому найден риск; связь с текстом правила — через snapshot анализа (а не FK: правило могло измениться после анализа).
- Snapshot анализа: `snapshot["risk_rules"] = [{id, code, revision, title, category, kind, description, signs, severity, recommendation}]`. `PIPELINE_VERSION` повысить.
- Удаление документа и анализов (`purge_document`, политика хранения) работают без изменений.

## 5. API и права

- `GET /api/admin/risk-rules` — список (Admin, Superadmin; включая архив по `?archived=true`).
- `POST /api/admin/risk-rules`, `PATCH /api/admin/risk-rules/{id}` (с `version` для оптимистичной блокировки → 409 при конфликте), `POST /api/admin/risk-rules/{id}/archive` — `policies.can_manage_risk_rules`; схемы `extra="forbid"`, ограничения длины; управляющие символы удаляются.
- `GET /api/risk-rules/available` — включённые неархивные правила для формы анализа (все, кто может запускать анализ): `id, code, title, category, kind, description, default_selected`.
- `POST /api/analyses` и `POST /api/analyses/estimate`: новое поле `rule_ids: list[UUID]` (по умолчанию пусто). Проверки: правило существует, включено, не в архиве, его категория среди выбранных, не больше лимита, суммарный размер блока ≤ лимита → иначе 422 (`risk_rule_unavailable`, `risk_rule_category_not_selected`, `risk_rules_limit_exceeded`).
- `retry` анализа берёт правила из snapshot (даже если правило с тех пор изменено, выключено или архивировано).
- Новые маршруты — в `test_security_sweep.py` (`SELF_ROUTES` для маршрутов без ID объекта).

## 6. Встраивание в конвейер (`backend/app/analysis/`)

- `prompts.py`: функция `org_rules_block(rules)` — блок
  ```
  <org_rules>
  <rule code="RR-003" category="penalties" kind="clause_risk">название; что искать; признаки; рекомендуемый уровень; рекомендация</rule>
  </org_rules>
  ```
  с экранированием (`escape`, как у фрагментов). Пояснение в системном сообщении: правила организации уточняют, **что** искать; они не меняют формат ответа, требования к доказательствам и правила анализа; риск по правилу сообщается только при наличии подтверждающей цитаты (кроме `missing_clause`); если найденный риск соответствует правилу — укажи `rule_code`, иначе `null`.
- `chunk_messages`: правила с `kind ∈ {clause_risk, any}` выбранных категорий; `cross_section_messages`: правила с `kind ∈ {missing_clause, any}`. Если правил нет — блок не добавляется (текст промпта прежний, кроме поля схемы).
- `schemas.py`: `RiskItem.rule_code: OptText16` (строка или null). Сервер проверяет код по snapshot: неизвестный код → `null` + отметка в `validation_notes` (`rule_code_unknown`), риск не отклоняется.
- `dedup.py`: при слиянии рисков сохраняется код правила (если у сливаемых разные коды — первый по уровню, остальные в `validation_notes.merged_rules`).
- Версии: `chunk-3`, `cross-3` в `PROMPT_VERSIONS`, `PIPELINE_VERSION` +1.
- Оценка объёма (`estimate`): размер блока правил × число частей + cross_section; предупреждение в форме, если правила увеличивают оценку больше чем на 25 %.
- Маскировка (этап 10): блок правил не маскируется (§1, вопрос 6); текст договора — как сейчас.
- `mock-llm` e2e-стенда: ответ с `rule_code` для сценария с правилом.

## 7. Frontend

- **Страница «Правила»** (`frontend/src/pages/admin/RiskRulesPage.tsx`, пункт меню для Admin/Superadmin): таблица (код, название, категория, тип, включено, по умолчанию), фильтр по категории, «Показать архив»; форма создания/редактирования (поля §3, счётчики символов, предупреждение о данных для облачных моделей), переключатели «Включено» и «По умолчанию» прямо в таблице, архивирование с подтверждением, история изменений (как `ModelPage`).
- **Новый анализ** (`NewAnalysisPage.tsx`, блок «Категории рисков»): под каждой категорией — её правила с отступом (флажок, код, название, подсказка с описанием). Снятие категории снимает и делает недоступными её правила; «Выбрать все» / «Снять все» действуют на правила; счётчик «Правил выбрано: N из лимита». При превышении лимита — сообщение, кнопка запуска неактивна.
- **Отчёт** (`RiskCard`, `RisksSection`, `AnalysisPage`): бейдж «Правило RR-003 · название» на карточке риска; фильтр «Правило» (в т.ч. «без правила»); в «Итогах» — «Применены правила организации: N» с раскрываемым списком (из snapshot, с ревизией).
- **Экспорт** (`app/exports/content.py`, `render.py`): колонка «Правило» в CSV/XLSX; в PDF/DOCX — строка у риска и список применённых правил в разделе параметров анализа.
- Тексты — `src/i18n/ru.ts`; схемы zod — `src/api/riskRules.ts`; фикстуры MSW — `src/test/riskRules.ts`.

## 8. Проверки этапа

Backend (unit):
- `org_rules_block`: экранирование `<`/`>`/кавычек, порядок, фильтрация по категории и типу, лимит размера;
- валидация `rule_code` (известный, неизвестный, null), сохранение кода при дедупликации;
- без правил промпт совпадает с прежним, кроме описания поля `rule_code`.

Backend (integration, `api`):
- CRUD правил: Admin/Superadmin — да, Analyst/Viewer — 403; конфликт версии — 409; ревизии и аудит без текста правила; архив скрывает правило из `available`;
- запуск с правилами: выключенное/архивное/чужой категории/сверх лимита → 422; `Recorder` mock-провайдера — блок `<org_rules>` есть в запросах chunks/cross_section только с выбранными правилами;
- риск с `rule_code` сохраняется с кодом; неизвестный код → null + отметка; цитата по-прежнему проходит шаг A, без цитаты `clause_risk` по правилу не подтверждается;
- `retry` после изменения и архивации правила использует текст из snapshot;
- экспорт содержит правило; security sweep с новыми маршрутами; миграция — `alembic check`, тест на отсутствие разрушительного SQL.

Frontend (Vitest/MSW): страница правил по ролям, форма и ошибки сервера, вложенные флажки в форме анализа (снятие категории, «Выбрать все», лимит), бейдж и фильтр в отчёте.

E2E: в сценарий `flow` — создать правило, запустить анализ с ним на `e2e-mock`, увидеть бейдж в отчёте и колонку в CSV.

Live (по согласованию, ≈ 0,01 USD): 2–3 правила на договорах `samples/` с `qwen/qwen3.6-35b-a3b` (рассуждения выключены) или `gpt-4o-mini` — сравнить с прогоном без правил: найдены ли риски по правилам, нет ли ложных срабатываний и роста отклонённых рисков. Фактические числа — в IMPLEMENTATION_STATUS.
